# gap:flutter-api-contract

## summary
I read the files you listed in full: api_service.dart, web_service.dart, const.dart, update_checker.dart, socketservice.dart, login_controller.dart, login_screen.dart, sign_in_with_email_screen.dart, user_service.dart, common_service.dart, notification_service.dart, session_manager.dart, subscription_manager.dart, personal_info_controller.dart, splash_controller.dart, main.dart, chat_tag.dart and chatting_controller.dart. I also grepped every WebService.* call site, editProfile caller and socket emit, and checked them against the API route files. Note that this source tree may not match the build users actually have installed. Every REST call goes through ApiService except two: NotificationService.commonSend (raw http.post, but it reuses ApiService.shared.header and points at a route that does not exist), and the APK download in the update screen (plain GET). When nobody is logged in, the Authorization header is still sent as an empty "Bearer ", because SessionManager.getToken returns "" rather than null. The server reads that as no token. The only auth flows a user can reach are firebase-google-login and firebase-email-register. Email sign-in and email sign-up both call firebase-email-register, and both Google and email always send firebaseToken plus firebaseUid. OTP, loginWithEmail, registerWithEmail and firebase-email-login are defined but nothing can reach them. firebase-login, verify-otp-with-name and complete-profile are not referenced anywhere in the app. Almost every user call sends the caller's identity in the body as user_id, my_user_id or userA_id. Only fetchProfile already goes through `authenticate`, and the app calls it at every launch, so a JWT older than 7 days sends the user back to the login screen. The socket handshake sends no auth at all. 'join' and the badge-count events send a bare userId string, and send_message trusts a senderId supplied by the client. Chat text is shown with a plain Text() widget, with no HTML, Linkify or RichText, so a malicious message cannot inject markup in the app. editProfile can send is_verified (from subscription_manager) and gender (from personal info), but never membership, phone or email. The update checker does block the user when isMandatoryUpdate is set. It only runs from the splash screen, though, and only after fetchProfile succeeds. Users whose token has expired, or who are rejected after hardening, never see the update prompt. So to force an update you have to leave fetchSetting, fetchProfile and /api/download-apk working with today's behaviour. The Firebase key used by confirmPasswordReset is exactly the Android current_key for socialmedia-dcdd8. Whether that key has an Android-app restriction cannot be checked from the code.

## findings (10)

### [HIGH][security] Logout keeps the JWT and user record, and the next launch reconnects the socket as the logged-out user
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/screens/setting_screen/setting_controller.dart:93
- evidence: setting_controller.dart:93-94 `void cleanAllSession() { SessionManager.shared.setLogin(false);` (setUser(null), Purchases.logOut and the logOut API call are all commented out, lines 85-100). splash_controller.dart:26-33 `if (SessionManager.shared.getUser()?.id != null) { UserService.shared.fetchMyProfile(... SessionManager.shared.setUser(user); SocketService.shared.startCommonListening();`
- impact: After logout the token stays in GetStorage key 'device_token_bearer'. ApiService keeps sending it as a Bearer token. On the next launch the splash screen calls fetchProfile with it and connects the socket (join with the old userId), even though isLogin is false and the onboarding screen is showing. On a shared phone, the previous user's session stays live and keeps receiving chat events.
- fix: In the next app build, make cleanAllSession call SessionManager.shared.clear() (or remove the token and user), disconnect the socket, and call the real /api/auth/logout. On the server, add token revocation or a token version so that logging out actually invalidates the JWT.

### [HIGH][business-logic] The update prompt never appears for users whose fetchProfile call fails, so a forced update cannot reach them
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/screens/splash_screen/splash_controller.dart:46
- evidence: splash_controller.dart:46-56 `void fetchSettings() { fetchUser(() { CommonService.shared.fetchGlobalSettings((p0) { if (p0) { UpdateChecker.shared.checkForUpdates();` and lines 35-37 `} else { SessionManager.shared.setLogin(false); Get.offAll(() => const LoginScreen());` (completion is never called). AuthController.js:17 `{ expiresIn: '7d' }`
- impact: If a stored user's fetchProfile returns 401, the splash screen jumps straight to LoginScreen and never fetches settings or runs the update check. This happens when the JWT is more than 7 days old, or if hardening starts rejecting old clients. None of the login flows run the update check afterwards. The only other entry point is the manual button at setting_screen.dart:141, which reads cached settings. A mandatory update can therefore only reach users who are logged out with no stored user, or who logged in within the last 7 days.
- fix: Before hardening, ship a build that runs the update check right after fetchGlobalSettings, independent of fetchUser and also after login. Keep /api/fetchSetting and GET /api/download-apk public. Do not change how fetchProfile responds to old clients until most users have updated.

### [HIGH][security] The app can send is_verified 0 or 3 to editProfile, and the API writes it to the user record
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/common/managers/subscription_manager.dart:60
- evidence: subscription_manager.dart:58-63 `Purchases.addCustomerInfoUpdateListener((customerInfo) async { checkSubscription(customerInfo); UserService.shared.editProfile( isVerified: isSubscribe ? 3 : 0,`. user_service.dart:577-578 `if (isVerified != null) { param[Param.isVerified] = isVerified;` (params.dart:46 `isVerified = 'is_verified'`). API UserController.js:335 `if (is_verified !== undefined) user.is_verified = Boolean(is_verified);`
- impact: Any RevenueCat customer-info update would un-verify a verified user (0 becomes false) or self-verify one (3 becomes true). RevenueCat is only configured when its key is non-empty. The Android key is '' (const.dart:14) and the iOS key is the placeholder 'your_ios_revenuecat_api_key' (const.dart:13), so this may not fire today. Separately, anyone can POST is_verified or membership with any user_id.
- fix: In the API editProfile, ignore is_verified, membership, role and is_block from the body. Nothing in the app needs those values to be accepted, so dropping them breaks nothing. Remove the listener's editProfile call in the next app build.

### [MEDIUM][security] The socket handshake has no auth, and identity comes from client-supplied userId and senderId
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/screens/chats_screen/socketservice.dart:23
- evidence: socketservice.dart:23-31 `socket = IO.io(baseUrl, { 'transports': ['websocket'], 'autoConnect': true, }); socket.onConnect((_) { ... socket.emit('join', userId);` and line 101 `socket.emit('send_message', { 'senderId': senderId, 'receiverId': receiverId, 'content': content, 'type': type,`
- impact: Installed apps send no token, cookie or extraHeaders. 'join' sends the raw userId string (or '0' if no user is stored). If the server makes handshake auth mandatory, every installed app loses chat and badge counts. If it doesn't, anyone can join as any user. Events that carry identity: join(userId), get_notification_count/get_match_request_count/get_unread_chatroom_count(userId), send_message{senderId,receiverId,content,type}, mark_seen{roomId,receiverId=myId}, typing/stop_typing{toUserId,fromUserId}, accept_chat/reject_chat/decline_chat{roomId}, join_icebreaker_queue{userId,preferences}, submit_answer, reveal_identity{gameId}, leave_icebreaker_queue.
- fix: Server side: accept handshake.auth.token or handshake.headers.authorization when present and bind socket.userId to it. Ignore the client's userId and senderId whenever an authenticated id exists. Only allow unauthenticated legacy joins during a sunset window. App side: pass 'auth': {'token': SessionManager.shared.getToken()} or extraHeaders in IO.io.

### [MEDIUM][security] An empty 'Authorization: Bearer ' header is sent when logged out, and multipart uploads use a cached token
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/common/api_service/api_service.dart:27
- evidence: api_service.dart:27 `if (_token != null) 'Authorization': 'Bearer $_token',` and session_manager.dart:38-40 `String getToken() { return storage.read(SessionKeys.token) ?? ""; }`. multiPartCallApi (api_service.dart:149-171) never calls loadToken() and runs `request.headers.addAll(header);`
- impact: Because getToken() returns "", the _token != null check always passes. Before login, every request carries 'Bearer ' with nothing after it. authMiddleware.js:6 `split(' ')[1]` turns that into "" and treats it as missing, which is fine, but a stricter parser could return 401 instead of treating the call as public. Multipart editProfile and uploadUserPhotos reuse whatever token the last call() loaded.
- fix: Server: treat an empty or whitespace bearer token as absent on public routes. App (next build): send the header only when the token is non-empty, and call loadToken() in multiPartCallApi.

### [MEDIUM][infra] The server's password-reset call uses the Android Firebase key, which may be restricted
- where: /var/www/banjaramatch.com/banjaramatch_app/android/app/google-services.json:40
- evidence: google-services.json:3-13 `"project_number": "799990198329"`, `"project_id": "socialmedia-dcdd8"`, `"package_name": "com.banjaramatch"`; line 40 `"current_key": "AIza<redacted-firebase-web-key>"`. API AuthController.js:1166 `accounts:resetPassword?key=AIza<redacted-firebase-web-key>`. The iOS plist uses a different key (GoogleService-Info.plist:12 `AIza<redacted-key>`). serviceAccountKey.json project_id is also socialmedia-dcdd8.
- impact: The key is confirmed to be the Android key for socialmedia-dcdd8. If it has an 'Android apps' application restriction in GCP, server-side Identity Toolkit calls are rejected with 403 (API_KEY_ANDROID_APP_BLOCKED), because a Node server sends no X-Android-Package or X-Android-Cert headers. That would break confirm-password-reset. Firebase's auto-created keys are usually unrestricted by default; the restriction cannot be verified from the code. The app itself never calls verify-password-reset-code or confirm-password-reset; it uses FirebaseAuth.sendPasswordResetEmail (sign_in_with_email_screen.dart:295).
- fix: Create a separate server-only key, restricted by API (Identity Toolkit) and IP, and load it from env. Or move to Admin SDK flows. Check in the GCP console what restrictions the current key has.

### [MEDIUM][data-integrity] Email sign-in uses the register endpoint and sends the email exactly as typed
- where: /var/www/banjaramatch.com/banjaramatch_app/lib/screens/login_screen/sign_in_with_email_screen.dart:172
- evidence: sign_in_with_email_screen.dart:172-176 `UserService.shared.firebaseEmailRegister( fullName: firebaseUser.displayName ?? emailController.text.split('@')[0], email: emailController.text.trim(), firebaseUid: firebaseUid, firebaseToken: firebaseToken ?? '',`
- impact: Both sign-in and sign-up go to /api/auth/firebase-email-register; firebase-email-login is never called. The email is the raw text (only trimmed, not lowercased). If the server switches to decodedToken.email, which Firebase lowercases, existing accounts stored with mixed-case emails will not match User.findOne({email}). firebaseToken falls back to '' if getIdToken returns null.
- fix: When making firebaseToken mandatory, derive uid and email from the decoded token and match emails case-insensitively, or normalise them in a migration. Keep firebase-email-register's existing 'auto login' behaviour.

### [LOW][security] deleteRoom takes both user ids from participant order, not from the session

## open_questions
- Is this source tree what users actually have installed (versionCode 3)? It is not a git repo, so there is no way to confirm that older builds don't call other endpoints, such as verify-otp.
- How is the Android app distributed: Play Store or sideloaded APK via /api/download-apk? The in-app updater only works for sideloaded installs. Play Store users would need Play in-app updates or a store release.
- Is there a shipped iOS build? GoogleService-Info.plist exists, but RevenueCat iOS key is a placeholder and Apple login is commented out.
- In GCP, what application and API restrictions does the key AIza<redacted-firebase-web-key> have? This decides whether the server's confirm-password-reset works.
- Should gender be editable only while it is empty or 'Not specified'? The app's onboarding sends gender through editProfile, so a hard lock would break onboarding for new users.
- How long should the legacy window be (unauthenticated socket join, body user_id fallback)? It should be based on how many active users run a build that includes the token-aware socket and update-check fixes.
