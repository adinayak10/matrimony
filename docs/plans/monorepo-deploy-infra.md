3. **Node 22.23.2** (`.nvmrc`), interpreter as an absolute path. The pm2 daemon runs `/usr/bin/node` 18.19.1, so `interpreter: 'node'` keeps Node 18 forever. Node-22 risks checked: all remaining deps are pure JS and support >=18 (firebase-admin 13, mongoose 8.16, socket.io 4.8, multer 1.4.5-lts, express 5.1). Real gotcha: Node 17+ resolves `localhost` IPv6-first and `/etc/hosts` has `::1 localhost` → every loopback URL/URI must be literal `127.0.0.1` (web `AUTH_SERVER_URL`, api `MONGODB_URI`, admin `API_BASE_URL`, nginx `proxy_pass`). The bridge start (B4 step 10) is the Node-22 test before any traffic.
4. **pm2 = `exec_mode: 'cluster', instances: 1, wait_ready: true`** for web/api/admin. Only cluster mode gives overlapped reloads (new process is up before the old one is killed); fork-mode "reload" is a restart with a port gap. `instances` stays 1 for the API (socket.io + gamesocket state in memory, no Redis adapter). Verified in `/usr/local/lib/node_modules/pm2/lib/API.js:1612` (`delete appConf.exec_mode`) that `startOrReload` can never change exec_mode of a running app → the one-time cutover must `pm2 delete` + `pm2 start`; from then on `pm2 startOrReload ecosystem.config.js --update-env` is a real reload (cwd/script/interpreter/env are re-read from the file each time, API.js:1060-1072).
5. **Cutover = bridge processes on 4100/4101/4102 + two nginx reloads (zero 502s).** Fallback: `pm2 delete old && pm2 start ecosystem.config.js` (2-5 s of 502 per app). `startOrReload` is wrong for the cutover for the reason in 4 plus it would carry the old `cwd`.
6. **Deploy style = in-place checkout + webhook + rollback-to-previous-sha** (live feribazaar hook), with the `--update-env` secret leak fixed (listener spawns `deploy.sh` with a minimal env and `deploy.sh` `unset`s `WEBHOOK_SECRET`).
7. **Fresh git history.** Old `matrimony-api` is archived on GitHub (not force-pushed, not deleted yet); its 20 uncommitted changes + 152 untracked files are captured by building `apps/api` from the WORKING TREE and by a local-only tarball + patch (never pushed: the tree holds secrets and photos).
8. **Secrets never in git.** `config.json` is only read for `port` and a dead SSL branch (`index.js:10,21,121`) → replace with env, archive the file in `SHARED/secrets`. Firebase key via `FIREBASE_SERVICE_ACCOUNT_PATH`. Rotation (JWT_SECRET is the public default per crit list; Firebase SA key; APNs key; admin password) is an owner action scheduled AFTER cutover (B4 M4), so no session is invalidated by the migration itself.
9. **Uploads/downloads/sitemaps/blog-images live in SHARED** and are symlinked into the checkout by `deploy.sh link_shared` (feribazaar `deploy/deploy.sh:188-215`). Nothing under those paths is ever tracked, or `git reset --hard` would replace the symlink with a directory.

## risks
- git reset --hard destroys runtime data if any runtime path is ever tracked (old repo tracked 216 upload files). Mitigation: .gitignore written before the first add; first-commit `git ls-files` grep gate; link_shared() refuses to recurse into a symlink; deploy.sh never runs `git clean`.
- Node 18 -> 22 behaviour change: `localhost` resolves to ::1 first; apps bound to 127.0.0.1 only. Mitigation: every loopback URL/URI is literal 127.0.0.1 (web AUTH_SERVER_URL/API_URL, api MONGODB_URI/FRONTEND_URL, admin API_BASE_URL, nginx upstreams); check-env.js enforces it; the bridge start exercises Node 22 before any traffic.
- pm2 `startOrReload` cannot change exec_mode (API.js:1612) and would keep the old cwd; using it for the cutover would leave the old code running. Mitigation: cutover is bridge + `pm2 delete` + `pm2 start ecosystem.config.js`; `startOrReload` only afterwards.
- Admin blog image uploads break silently after the move (blogController.js:10 relative path into the web tree). Mitigation: BLOG_IMAGE_DIR env + SHARED/blog-images symlinked at apps/web/public/images/blog; template 1.jpg/2.jpg/3.jpg copied into SHARED (index.ejs:2267-2276 reference them).
- Workspace hoisting puts the wrong express/dotenv/bcryptjs major in front of an app. Mitigation: explicit `node -p require('express/package.json').version` check per app after npm install; fallback `npm ci --install-strategy=nested`; undeclared api deps declared.
- npm ci during a deploy on a box with ~500 MB free RAM and 1.9 GB swap in use can thrash or OOM. Mitigation: npm ci only when package-lock.json changed between GOOD and SHA; NODE_OPTIONS=--max-old-space-size=768; --omit=dev; rollback path re-runs it only if needed.
- Deploy secret leaks into app env through pm2 --update-env (observed on feribazaar). Mitigation: listener keeps WEBHOOK_SECRET out of process.env and spawns deploy.sh with a minimal env; deploy.sh unsets it; manual pm2 commands should go through deploy.sh.
- nginx change breaks a tenant or a slug. Mitigation: only the three banjaramatch site files change (server_name/ports identical; gzip/server_tokens set in server context, not nginx.conf); `nginx -t` gate with .prev restore in deploy.sh; check-urls.sh before/after diff; static locations copy the exact Cache-Control values Express sends today.
- Forced-update path for installed apps breaks if fetchSetting/fetchProfile/download-apk or the api host change. Mitigation: host, /api, /socket.io, /uploads paths unchanged; download-apk still Node-served via the uploads symlink; JWT_SECRET rotation deferred to M4 and coordinated with Track D's update-check build.
- Rotating JWT_SECRET logs every web/app/admin user out once. Mitigation: cutover keeps the current value in all three env files; rotation is a separate, announced step.
- pm2-logrotate and the shared root pm2 daemon affect the other ~12 tenants' logs (rotation only, beneficial) and `pm2 save` rewrites dump.pm2 for all apps. Mitigation: run `pm2 save` only after `pm2 ls` shows every tenant online; never `pm2 kill`/`pm2 update`.
- GitHub webhook pointed at the apex host would receive a 301 and never deploy. Mitigation: payload URL is exactly https://www.banjaramatch.com/deploy-webhook; ping delivery checked in M3.
- Both old and bridge API processes run the 15/30-minute node-cron jobs for a few minutes during M0-M1. Mitigation: do M1-M2 within one window; jobs are idempotent monitors (ChatIntentMonitor/detectInterestMonitor) per schedular.js.
